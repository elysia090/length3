`deploy.sh` は最初、10行だった。

```sh
#!/bin/sh
cd /srv/app
APP_ENV=prod ./server
```

今は200行ある。誰も全部把握していない。

この既視感は、おそらく多くのエンジニアが一度は経験したことがある。
シェルスクリプトは書き始めが気持ちよく、気づいたときには誰も触りたくないものになっている。

ではなぜシェルスクリプトは膨らむのか。そして、なぜ既存のツールでは止まらないのか。
[gx](https://github.com/elysia090/gx) と [ccux](https://github.com/elysia090/ccux)、そして [llux](https://github.com/elysia090/llux) スタイルは、この問いに対してひとつの答えを提示している。

## シェルスクリプトが肥大化する本当の理由

表面的な理由は「要件が増えたから」だ。でも本質は別にある。

シェルは**手続き**を書くのが得意だが、**起動の状態**を宣言するのが苦手なのだ。

`deploy.sh` が200行になるまでに積み重なるのは、おおむね次のようなものだ:

- 環境変数のセット（と、うっかり引き継いでしまう変数のクリア）
- ワーキングディレクトリの変更
- ユーザー切り替え（`sudo -u appuser`）
- ファイルから秘密情報を読み込んで変数に突っ込む（`SECRET=$(cat /run/secrets/db)`）
- ロック取得（`flock` か何かで多重起動防止）
- タイムアウト
- ログのリダイレクト

これらは本来、互いに独立した「起動の関心事」だ。
しかしシェルスクリプトにはそれを分離する構造がない。全部が一本のスクリプトの中で、順番に、手続きとして書かれる。

結果として起きるのは**関心事の混在**だ。「タイムアウトだけ変えたい」のに、その前後の環境変数セットのコードも読まなければならない。「秘密情報の読み込みパスを変えたい」のに、ロック処理のコードを挟んで変更箇所を探す。

## 既存ツールはなぜ止められないのか

「そのためのツールがある」という声は当然出てくる。

**direnv** はディレクトリ移動で環境変数を自動的に適用する。便利だが、「自動的に」が問題だ。いつ・どのタイミングで環境変数が変わるかが、ディレクトリという外部状態に依存する。読み返しにくく、再現しにくい。

**`docker run --env-file`** はファイルから環境変数を渡せる。しかし Docker はそもそも「環境の封じ込め」が目的のツールだ。ファイルを環境変数に変換するだけのためにコンテナを持ち出すのは、蚊を殺すためにバズーカを撃つに近い。

**systemd / launchd** はプロセス起動を設定ファイルで管理する。デーモン管理には適しているが、開発ループや単発の起動制御には、設定の複雑さが重すぎる。

**make / just / task** はタスクランナーだ。「何を実行するか」を管理するが、「どういう状態でプロセスを起動するか」は管理しない。

これらに共通する欠落がある。**起動の意図をデータとして扱い、実行前に検査する**という概念が、どのツールにもない。

## gx：inspect-first という文化

[gx](https://github.com/elysia090/gx) が最初に提供するのは `gx exec` でも `gx run` でもなく、**`gx inspect`** だ。

```sh
gx inspect \
  --clear-env \
  --env APP_ENV=prod \
  --env PORT=8080 \
  --chdir /srv/app \
  --user appuser \
  -- ./server
```

これを実行すると、プロセスは起動しない。代わりに正規化された起動プランが出力される:

```json
{
  "schema": "gx/v1",
  "argv": ["./server"],
  "env": {
    "APP_ENV": "prod",
    "PORT": "8080"
  },
  "cwd": "/srv/app",
  "user": "appuser",
  "clear_env": true
}
```

これは何がうれしいのか。

まず、**レビューできる**。PR に `gx inspect` の出力を貼れば、「この起動でどんな環境変数が渡るか」がコードレビューで確認できる。シェルスクリプトの変数展開を頭の中でトレースする作業がなくなる。

次に、**テストできる**。CI パイプラインで `gx inspect | jq '.env.APP_ENV == "prod"'` を実行すれば、起動設定の回帰テストになる。実行せずに検証できる。

そして、**変更が局所化できる**。タイムアウトを変えたいなら、タイムアウトを担当する層（llux スタイルでは `ttmx`）だけを変える。gx の設定を触る必要はない。

`gx exec` と `gx run` の使い分けも明示的だ。`exec` は現在のプロセスを置換する（`execve` の直接呼び出し）。`run` は子プロセスとして起動する。この区別を「なんとなく」ではなく、コマンド名として表明する。

## ccux：「ファイルの中身」と「ファイルの場所」

[ccux](https://github.com/elysia090/ccux) が解決するのは、シェルスクリプトで頻出するこのパターンだ:

```sh
SECRET=$(cat /run/secrets/db_password)
CONFIG_PATH=/run/config/app.json
```

上の行は「ファイルの中身」を変数に入れている。下の行は「ファイルのパス」を変数に入れている。

これは微妙に異なる操作だが、シェルでは同じ見た目のコードになりやすい。そして「どちらが何か」は慣習とコメントに頼ることになる。

ccux はこの区別を **`--map` と `--map-path`** として明示する:

```sh
ccux inspect \
  --from /run/secrets \
  --map DB_PASSWORD=db_password \
  --map-path CONFIG_PATH=../config/app.json \
  -- ./server
```

`--map VAR=FILE` はファイルの中身を変数に注入する。
`--map-path VAR=FILE` は解決済みの絶対パスを変数に注入する。

`ccux inspect` の出力:

```json
{
  "schema": "ccux/v1",
  "mappings": [
    { "var": "DB_PASSWORD", "file": "/run/secrets/db_password", "mode": "value" },
    { "var": "CONFIG_PATH",  "file": "/run/config/app.json",    "mode": "path"  }
  ]
}
```

ファイルがどう扱われるかが、実行前に一目でわかる。

また `--from` でソースディレクトリを指定することで、マッピング定義がディレクトリ相対になる。起動設定を別の環境に持ち込むときに、ディレクトリを差し替えるだけで済む。

## llux スタイル：関心事を層として積む

[llux](https://github.com/elysia090/llux) はツールではなく、これらのツールをどう組み合わせるかの**スタイルガイド**だ。

推奨される起動スタック順はこうだ:

```
gx          ← 実行環境（env, user, cwd, umask, rlimit）
lockx       ← 多重起動防止（排他ロック）
ttmx        ← タイムアウト・グレースフルシャットダウン
ffdx        ← 標準入出力のルーティング（ログの向き先）
ccux        ← ファイル由来の入力（秘密情報・設定パス）
target      ← 実際のプログラム
```

これを組み合わせると、こうなる:

```sh
gx run \
  --clear-env \
  --env APP_ENV=prod \
  --chdir /srv/app \
  --user appuser \
  -- \
ccux exec \
  --from /run/app-inputs \
  --map DB_PASSWORD=db_password \
  --map-path CONFIG_PATH=config.json \
  -- ./server
```

**外から内へ**。左にあるほど「大きな起動条件」で、右（内側）にあるほど「ターゲット固有の入力」だ。

この構造の何がうれしいか。「ログの向き先を変えたい」なら `ffdx` の行だけを変える。「タイムアウトを変えたい」なら `ttmx` の行だけを変える。gx の行も ccux の行も触らなくていい。変更が**局所化**される。

シェルスクリプトが200行になったとき、「タイムアウトを変えるだけなのにどこを触ればいいかわからない」という問題が、この構造では原理的に起きにくい。

## ハッキーで面白いポイント

正直に言うと、gx と ccux を初めて見たとき「これは小さすぎないか」と思った。各ツールがやっていることは、それ単体では地味だ。

でも使い始めると、気づくことがある。

**シェルを排除すると、逆にシェルが見えてくる。**

gx が内部でやっているのは、つまるところ `execve` の呼び出しだ。しかしその手前で、環境変数の構築・ディレクトリ変更・ユーザー切り替えを「宣言的に」組み立てて、JSON としてシリアライズできる状態にする。

この「シリアライズできる」という性質が、実はハッカー的に面白い。

```sh
# 本番と開発で起動設定が同じかどうかをテストする
diff \
  <(gx inspect --env APP_ENV=prod -- ./server | jq '.env') \
  <(gx inspect --env APP_ENV=dev  -- ./server | jq '.env')
```

起動設定が「データ」になると、パイプで流せる。`jq` で加工できる。CI で diff できる。

ccux も同様だ。`ccux inspect` の JSON 出力をパースして、「このファイルがマップされているか」「このパスは絶対パスになっているか」を自動チェックできる。実際に起動しなくても、起動の前提条件をテストできる。

**クォーティング地獄からの解放**も大きい。シェルスクリプトで環境変数に特殊文字を含む値を渡すとき、クォートのエスケープは本当に難しい。gx は引数をシェルを介さずに直接 `execve` に渡すため、この問題がそもそも発生しない。

そして最もハッカー的に美しいと思うのは、**これが「再発明」ではないという点**だ。

Unix の `execve` は昔からある。環境変数も昔からある。ファイルから変数を読む操作も、ユーザー切り替えも、全部 Unix の基本機能だ。

gx と ccux がやっているのは、それらの操作を「意図として表明できる形」に整えることだ。既存の機能を置き換えているのではなく、既存の機能を「見えるようにしている」。

## 起動は設計の一部だ

`deploy.sh` が肥大化するのは、起動の設計を設計として扱っていないからだ。シェルスクリプトに「とりあえず追記する」ことで、起動の関心事がインライン化されていく。

gx と ccux、そして llux スタイルが問いかけているのは、「起動の意図を、設計として外に出せないか」ということだ。

inspect-first。変更の局所化。層の明示。

これはシェルを否定していない。むしろ、シェルの責任を「プロセス管理」から「オーケストレーション」に絞ることで、シェル本来の力が生きる。

最後に、llux のドキュメントにある一文を引用して終わりにする:

> The goal is not to make commands shorter. The goal is to make launch intent easier to read, review, inspect, and change.

コマンドを短くしたいわけじゃない。起動の意図を、読んで・レビューして・検査して・変えられるようにしたい。

`deploy.sh` が怪物になる前に、読んでおきたいスタイルガイドがここにある。
