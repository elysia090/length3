**length3** is a technical blog engineered as a portfolio piece: every architectural decision is deliberate, every dependency earns its place, and the reading experience is treated as a first-class concern.
This article documents the full stack — from content pipeline to edge deployment — so you can understand what was built and why.

## Architecture Overview

The stack has three layers:

| Layer     | Technology                                   |
| --------- | -------------------------------------------- |
| Framework | Astro 6 (static output + Cloudflare adapter) |
| Content   | MDX + Content Layer API (Zod-validated)      |
| Runtime   | Cloudflare Workers (edge-native)             |

The blog is statically generated at build time (`output: 'static'`).
Static pages, fonts, and the Pagefind index are served as Cloudflare Pages assets at the edge.

## Content System

### Content Layer API and Zod Schema

Every article lives in `src/content/blog/` as either `.md` or `.mdx`.
The collection is defined with a strict Zod schema:

```typescript
const blog = defineCollection({
  loader: glob({
    pattern: '**/*.{md,mdx}',
    base: './src/content/blog',
  }),
  schema: z.object({
    title: z.string(),
    description: z.string(),
    publishDate: z.coerce.date(),
    updatedDate: z.coerce.date().optional(),
    tags: z.array(z.string()).default([]),
    draft: z.boolean().default(false),
    lang: z.enum(['en', 'ja']).default('en'),
  }),
});
```

The `z.coerce.date()` call lets you write `2026-03-20` in frontmatter and get a native `Date` object — no manual parsing.
`draft: true` excludes a post from all listing pages via a shared predicate:

```typescript
export const notDraft = (entry: BlogPost) => !entry.data.draft;
// Usage:
const allPosts = await getCollection('blog', notDraft);
```

### Frontmatter Fields

| Field         | Type           | Purpose                                                   |
| ------------- | -------------- | --------------------------------------------------------- |
| `title`       | `string`       | Required. Article heading and `<title>`                   |
| `description` | `string`       | Required. Lead paragraph and meta description             |
| `publishDate` | `YYYY-MM-DD`   | Required. Shown in article header and sort order          |
| `updatedDate` | `YYYY-MM-DD`   | Optional. Shown as "(upd. …)" next to publish date        |
| `tags`        | `string[]`     | Routed to `/tags/[slug]`, CJK-safe slugification          |
| `draft`       | `boolean`      | Defaults `false`. `true` hides the post from all listings |
| `lang`        | `'en' \| 'ja'` | Controls date format and `lang` attribute                 |

### MDX and Component Imports

MDX lets you import Astro components directly into article prose.
The `RubyText` component, for example, wraps a base text and its phonetic reading into a proper `<ruby>` element:

```astro
---
interface Props {
  base: string;
  reading: string;
}
const { base, reading } = Astro.props;
---

<ruby>{base}<rp>(</rp><rt>{reading}</rt><rp>)</rp></ruby>
```

In an article you write:

```mdx
import RubyText from '../../components/RubyText.astro';

<RubyText base="東京" reading="とうきょう" />
は日本の首都です。
```

Which renders as: <RubyText base="東京" reading="とうきょう" />は日本の首都です。

The `<rp>` fallback parentheses are included so the annotation degrades gracefully in browsers or screen readers that do not support `<ruby>`.

## Article Layout and Navigation

### Three-Column Shell

The article page uses a CSS grid with three columns:

```
[ TOC (sticky) ] [ prose (680px measure) ] [ empty right margin ]
```

The right column is deliberately empty — no widgets, no related posts, no ads.
Hierarchy comes from spacing and typography alone, following a print-editorial model.

### Table of Contents

The `TableOfContents` component extracts `h2` and `h3` headings from the MDX render tree and renders an accessible `<nav>`:

- **Desktop (≥ 720px):** TOC stays visible in the left rail as secondary navigation
- **Mobile (< 720px):** TOC is hidden so the reader reaches title and prose immediately
- **Active section:** an `IntersectionObserver` tracks which heading is in the top 45% of the viewport and highlights the corresponding TOC link in amber
- **Fade-out:** a second observer watches a sentinel element at the end of the article body; once the reader scrolls past it, the TOC fades to `opacity: 0` with `pointer-events: none`
- **Smooth scroll:** TOC link clicks call `scrollIntoView()` and push the hash to `history` without a hard jump

### Reading Time

Reading time is estimated with a CJK-aware regex-based algorithm:

```typescript
export function estimateReadingTime(text: string): number {
  const cjkChars = text.match(/[\u3000-\u9FFF\uF900-\uFAFF]/gu)?.length ?? 0;
  const latinWords = text.replace(/[\u3000-\u9FFF\uF900-\uFAFF]/gu, ' ').match(/\S+/g)?.length ?? 0;

  // CJK reading ~400 chars/min, Latin ~200 words/min
  const minutes = cjkChars / 400 + latinWords / 200;
  return Math.max(1, Math.ceil(minutes));
}
```

The implementation keeps the rules simple: CJK characters are counted directly, non-CJK tokens are counted with a whitespace split, and the result is rounded up to a minimum of one minute.

## Tag System

Tags are normalized into canonical slugs so CJK tags survive the transformation and punctuation-heavy names stay routable:

```typescript
export function canonicalizeTagSlug(tag: string): string {
  return tag
    .normalize('NFKC')
    .trim()
    .toLowerCase()
    .replace(/\s+/g, '-')
    .replace(/[^\p{L}\p{N}-]/gu, '')
    .replace(/-+/g, '-')
    .replace(/^-+|-+$/g, '');
}
```

Unicode property escapes keep `機械学習` intact, while punctuation cleanup and hyphen collapsing make names like `TypeScript / JS` converge to a stable canonical route.

Tag archive pages are generated at `/tags/[tag]` via `getStaticPaths`.
The `buildTagRoutes` utility centralises aggregation so the topic directory and per-tag listing pages share the same routing model:

```typescript
export function buildTagRoutes(posts: BlogPost[]): TagRoute[] {
  // Canonical slugs are collision-safe and deterministic.
}
```

## Full-Text Search with Pagefind

Search is powered by [Pagefind](https://pagefind.app/), a static-site search library that runs entirely at the edge with no external service.

The build pipeline:

1. `astro build` generates the static HTML output in `dist/`
2. `postbuild` runs `pagefind --site dist`, which crawls the HTML, indexes every `data-pagefind-body` element, and emits a binary search index alongside the static files
3. On the client, Pagefind's WASM engine loads the index from the same CDN edge node that serves the page — zero extra round-trips

The article body is annotated `data-pagefind-body` in `ArticleLayout.astro`:

```astro
<article class="prose" data-pagefind-body lang={lang}></article>
```

This scopes indexing to article content, excluding header, footer, and sidebar noise.

## Typography

### Fraunces Variable Font

Display headings use [Fraunces](https://github.com/undercasetype/Fraunces), a variable optical-size serif with a distinctive softness.
The font files (`Fraunces-Variable.woff2`, `Fraunces-Italic-Variable.woff2`) are self-hosted under `public/fonts/` and declared with `font-display: optional` so first paint can fall back immediately while repeat visits reuse the cached face.

### Font Stack

```css
--font-display: 'Fraunces', 'Hiragino Mincho ProN', 'Yu Mincho', Georgia, 'Noto Sans JP', serif;

--font-sans:
  'Noto Sans JP', 'Hiragino Kaku Gothic ProN', 'Yu Gothic UI', 'Meiryo', system-ui, sans-serif;

--font-mono:
  'JetBrains Mono', ui-monospace, 'Fira Code', 'Cascadia Code', 'Noto Sans JP',
  'Hiragino Kaku Gothic ProN', 'Yu Gothic UI', 'Meiryo', monospace;
```

Japanese mincho fallbacks are placed _before_ `Georgia` in the display stack so that CJK characters in headings render in a matching serif/mincho style.
Japanese sans-serif fonts are listed _before_ `system-ui` so that CJK body text still resolves cleanly on machines that only have local Japanese fonts installed.

### Japanese Typography Features

The blog has first-class support for Japanese composition:

- **`<ruby>` annotations** via the `RubyText` component — e.g. <RubyText base="情報処理" reading="じょうほうしょり" />
- **`line-break: strict`** — prevents breaks before small kana (ぁぃぅぇぉ…) and other restricted characters
- **`text-wrap: pretty`** — multi-line headings break at semantically reasonable points
- **`font-feature-settings: 'palt'`** — proportional alternate spacing for punctuation (。、…) tightens the visual rhythm of CJK text
- **`text-autospace: ideograph-alpha`** — automatic thin-space insertion between CJK and Latin characters, so `Astro 6` embedded in Japanese prose reads naturally

### Amber Accent

The single accent colour throughout the UI is amber (`#d4820a` for decorative elements, `#b45309` for text/interactive elements to meet WCAG AA at 4.5:1).
It appears on: the amber rule under article titles, TOC active-section indicators, tag links, and dates.
Everything else is ink (`#1c1a18`) and paper (`#f9f8f5`).

## Developer Experience

### TypeScript in Strict Mode

`tsconfig.json` enables `strict: true`.
All content collection types flow from `CollectionEntry<'blog'>` through `ProcessedPost` to each page component — there is no `any` in the data path.

### Biome and Prettier

Linting and formatting use two tools with complementary scopes:

| Tool                                                       | Target                          |
| ---------------------------------------------------------- | ------------------------------- |
| [Biome](https://biomejs.dev/)                              | `*.ts`, `*.tsx` — lint + format |
| [Prettier](https://prettier.io/) + `prettier-plugin-astro` | `*.astro` — format only         |

Biome keeps TypeScript linting and formatting in one tool, while Prettier handles Astro templates.

### Husky Pre-commit Hooks

`lint-staged` runs automatically on `git commit` via Husky:

```json
"lint-staged": {
  "src/**/*.{ts,tsx}":  ["biome check --write", "biome format --write"],
  "src/**/*.astro":     ["prettier --write"],
  "*.{json,md}":        ["prettier --write"]
}
```

This guarantees that no unformatted code reaches the repository without interrupting the development flow for in-progress files.

### Testing

| Suite      | Tool       | Scope                                                                          |
| ---------- | ---------- | ------------------------------------------------------------------------------ |
| Unit       | Vitest 4   | `estimateReadingTime`, canonical tag routing, `TagResolver`, `formatDate`      |
| End-to-end | Playwright | Article rendering, dev search fallback, built-search behaviour, tag navigation |

Vitest shares the Vite config and runs in `node` environment, which means TypeScript compilation is handled by the same pipeline as the main build.
Playwright is kept as a smoke suite against the dev server, while browser interaction logic is covered in Vitest with `jsdom`.

## Deployment

### Cloudflare Workers + Pages

The site is deployed to Cloudflare's global network via [Wrangler](https://developers.cloudflare.com/workers/wrangler/):

```toml
# wrangler.toml
name = "length3"
compatibility_date = "2025-01-01"
```

The `@astrojs/cloudflare` adapter wraps the Astro build output into a Worker bundle.
Static assets (HTML, CSS, fonts, Pagefind index) are uploaded as Cloudflare Pages assets.

The Vite SSR target is set to `'webworker'` so that Node.js-specific modules (like `fs`) are excluded from the bundle:

```javascript
vite: {
  ssr: {
    target: 'webworker',
  },
}
```

### CI/CD

GitHub Actions runs two workflows:

- **`ci.yml`** — on every push and PR: `astro check`, `biome check`, `vitest run`, `playwright test`
- **`deploy.yml`** — on push to `main`: `astro build` → `pagefind --site dist` → `wrangler deploy`

The `postbuild` npm script ensures the Pagefind index is always generated immediately after the Astro build, keeping the deploy pipeline simple.

## Design Principles

length3 is designed as a **reading-first** interface.
Rather than feeling like a typical web app, it leans toward an editorial, print-like structure:

- **Restrained typography** — two weights of two typefaces, one accent colour
- **Generous whitespace** — hierarchy from spacing alone, not decorative borders
- **No sidebar on article pages** — the right column is intentionally empty
- **680 px prose measure** — optimised for comfortable line length across viewport sizes

The result is an interface whose character comes from spacing and type treatment rather than decoration.
