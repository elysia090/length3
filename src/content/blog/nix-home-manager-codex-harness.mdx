AI コーディングエージェントをローカルで動かすと、環境が汚染される。
ツールが勝手にパッケージを入れ、シェルが書き換えられ、半年後には何が何だかわからない状態になる。

Codex App を Nix + home-manager で「閉じ込める」設計にした。
やったことと、踏んだ罠を記録しておく。

## 前提：ハーネスとは何か

ここでの「ハーネス」は、エージェントが動く環境を宣言的・冪等に管理する枠組みのことを指す。

- エージェントが使えるツールは Nix パッケージとして明示する
- シェル初期化・環境変数・プロジェクト信頼リストは home-manager で管理する
- `home-manager switch` を叩けば常に同じ状態に戻る

これが目標。

## 基本構造

flake.nix の骨格だけ示す。WSL 上の Ubuntu 向けなので `homeConfigurations` を使う。

```nix
{
  inputs = {
    nixpkgs.url = "github:NixOS/nixpkgs/nixos-25.05";
    home-manager = {
      url = "github:nix-community/home-manager/release-25.05";
      inputs.nixpkgs.follows = "nixpkgs";
    };
  };

  outputs = { nixpkgs, home-manager, ... }: {
    homeConfigurations.primary = home-manager.lib.homeManagerConfiguration {
      pkgs = nixpkgs.legacyPackages.x86_64-linux;
      modules = [ ./homes/primary/home.nix ];
    };
  };
}
```

home.nix はモジュール分割する。最小限の構成：

```
homes/primary/
├── home.nix        # エントリポイント
├── shell.nix       # シェル設定
└── codex.nix       # Codex 固有の設定
```

## シェルの選択：bash に寄せる理由

ここが最大の罠だった。

### WSL とシンボリックリンクの相性

home-manager は多くの設定をシンボリックリンクで管理する。
`~/.zshrc` は実態として `/nix/store/xxx.../zshrc` を指すシンボリックリンクになる。

Codex App は Windows 側のアプリケーションだ。
WSL のサブシェルを起動する際、Windows 側のパス解決を経由する。
このとき `/nix/store/...` へのシンボリックリンクが WSL の名前空間で解決されず、
**シェルの初期化が壊れた状態で起動する**ことがある。

zsh の場合は `$ZDOTDIR` を使って初期化ファイルを切り替える設計が必要になるが、
`$ZDOTDIR` の設定自体が zsh の起動時に読まれる `.zshenv` に依存するため、
「シンボリックリンクが解決できない → `.zshenv` が読めない → `$ZDOTDIR` が設定されない → 通常の `~/.zshrc` が読まれる」
という連鎖が起きる。

これがシェルが「吸われる」状態だ。
Codex が用意したサンドボックス環境ではなく、ユーザーの通常の zshrc が読まれ、
starship・direnv・fzf などの初期化コードが走って環境変数やPATHが変わる。
ハーネスが機能しない。

### bash を使う

bash は初期化ファイルが単純だ。
`~/.bash_profile`（ログインシェル時）と `~/.bashrc`（インタラクティブ時）しかない。
Codex App が起動するサブシェルは非インタラクティブなので、
`~/.bashrc` の大半は読まれない（`[ -z "$PS1" ] && return` パターンが機能する）。

home.nix に以下を書く：

```nix
# shell.nix
{ pkgs, ... }: {
  programs.bash = {
    enable = true;
    # Codex セッション向けの最小エクスポートだけここに書く
    profileExtra = ''
      export SHELL="${pkgs.bash}/bin/bash"
    '';
  };

  # zsh はインタラクティブ専用として残しておいてよい
  programs.zsh.enable = true;

  # WSL のデフォルトシェルを bash に向ける
  home.sessionVariables.SHELL = "${pkgs.bash}/bin/bash";
}
```

`SHELL` 環境変数を明示的に bash に向けることで、
Codex が `$SHELL` を参照してサブプロセスを起動するときに bash が使われる。
zsh はターミナルで手動で起動する用として残す。

## パッケージ管理：プロジェクトローカルに閉じ込める

Codex に渡すツールチェインは `home.packages` に書かない。
**プロジェクトの `flake.nix` の `devShells` に書く**。

```nix
# プロジェクト側 flake.nix
devShells.default = pkgs.mkShell {
  packages = [ pkgs.nodejs pkgs.python3 pkgs.uv ];
};
```

home-manager 側には direnv + nix-direnv だけ入れる：

```nix
# shell.nix に追加
programs.direnv = {
  enable = true;
  nix-direnv.enable = true;
};
```

プロジェクトルートに `.envrc` を置くだけで、
Codex がそのディレクトリで作業するときは自動的に devShell が有効になる。
Codex がプロジェクト外に出れば元の環境に戻る。

## Codex の信頼設定を自動化する

Codex App は `config.toml` にプロジェクトパスを `trust_level = "trusted"` として明示しないと、
そのディレクトリでコードを実行できない。

毎回手で書くのは面倒なので、home-manager のアクティベーションで自動生成する。
ワークスペース一覧は一箇所で管理し、信頼設定と clone の両方に使い回す。

```nix
# codex.nix — ワークスペース一覧・信頼設定・clone を一箇所で管理
{ config, lib, ... }:
let
  workspaceRoot = "$HOME/workspaces";
  workspaces = [
    { slug = "myproject"; repo = "your-github/myproject"; }
    { slug = "another";   repo = "your-github/another"; }
  ];

  configToml = ''
    [core]
    editor = "code"

  '' + lib.concatMapStrings (ws: ''
    [projects."${workspaceRoot}/${ws.slug}"]
    trust_level = "trusted"

  '') workspaces;
in {
  # config.toml を再生成
  home.activation.codexConfig = lib.hm.dag.entryAfter [ "writeBoundary" ] ''
    mkdir -p "${config.xdg.configHome}/codex"
    cat > "${config.xdg.configHome}/codex/config.toml" << 'TOML'
    ${configToml}
    TOML
  '';

  # 未 clone のワークスペースを clone
  home.activation.codexWorkspaces = lib.hm.dag.entryAfter [ "writeBoundary" ] ''
    mkdir -p "${workspaceRoot}"
    ${lib.concatMapStrings (ws: ''
      if [ ! -d "${workspaceRoot}/${ws.slug}" ]; then
        git clone "https://github.com/${ws.repo}.git" \
          "${workspaceRoot}/${ws.slug}"
      fi
    '') workspaces}
  '';
}
```

`home-manager switch` のたびに `config.toml` が再生成される。
ワークスペースの追加・削除はこのリストを一行編集して再 switch するだけだ。

## WSLENV の同期

Windows 側の環境変数と WSL 側を橋渡しする `WSLENV` も宣言的に管理する。

アクティベーション時に PowerShell 経由で現在の `WSLENV` を読み取り、
必要なエントリを追加してから書き戻す：

```nix
home.activation.syncWslenv = lib.hm.dag.entryAfter [ "writeBoundary" ] ''
  # PowerShell が使える環境（WSL on Windows）のみ実行
  if command -v powershell.exe >/dev/null 2>&1; then
    current=$(powershell.exe -NoProfile -Command \
      "[Environment]::GetEnvironmentVariable('WSLENV', 'User')" \
      2>/dev/null || echo "")

    # 必要なエントリが既に含まれていれば何もしない
    if [[ "$current" != *"GITHUB_TOKEN"* ]]; then
      updated="''${current:+$current:}GITHUB_TOKEN/u"
      powershell.exe -NoProfile -Command \
        "[Environment]::SetEnvironmentVariable('WSLENV', '$updated', 'User')" \
        >/dev/null 2>&1 || true
    fi
  fi
'';
```

ここで `/u` フラグは「WSL→Windows の一方向に共有」を意味する。
MCP サーバーが必要とする環境変数をこの方式で渡す。

## Windows ACL とパス：Linux に寄せる

WSL とシンボリックリンクの問題には前節で触れたが、根本に ACL（アクセス制御リスト）の問題がある。

Codex App は Windows プロセスとして動く。
Windows 側からワークスペースを解決しようとすると、NTFS の DACL チェックを経由する。
WSL が作ったシンボリックリンク（特に `/nix/store/...` へのもの）は、
Windows の ACL モデルからは「パーミッションの曖昧なファイル」として扱われ、
アクセスが拒否されたり、パス解決が止まったりする。

解決策は単純だ。**ファイルの実体を Linux 側（WSL ファイルシステム）に置き、Windows 側のパスへの依存を断ち切る。**

```nix
# shell.nix
home.sessionVariables = {
  WORKSPACES_ROOT = "$HOME/workspaces";  # Linux パスのみ使う
};
```

Windows → WSL の橋渡しは WSLENV 経由の環境変数だけに絞る。
ファイルの実体を `C:\Users\...` 以下に置かない。これだけで ACL 起因のトラブルが大幅に減る。

ワークスペースを WSL 側に集約したあとは、Windows 側からのアクセスは `/mnt/c/...` 経由ではなく
UNC パス（`\\wsl.localhost\Ubuntu\...`）経由になる。
Codex App はこちらを使う設計になっているので問題ない。

## GitHub を正本にしたブランチ戦略

ワークスペースの状態は GitHub を正本として管理する。
ローカルは「GitHub の再現物」にすぎない、という前提を崩さない。

### なぜブランチを多めに切るか

現行モデルのコンテキスト理解は限定的だ。
長い文脈を渡して「全体を把握しながら作業させる」より、
**タスクをブランチ単位に分割して独立させた方が安定する**。

ブランチが増えるのは現行の宿命として受け入れる。

| 戦略 | メリット | デメリット |
|---|---|---|
| ブランチ多め | フォールバック耐性が高い。main を汚染しない | ブランチ管理コストが増える |
| ブランチ少なめ | 管理がシンプル | コンテキスト汚染が main に波及する |

現時点では前者が正解だ。
コンテキスト理解が向上すれば「main + 1 feature ブランチ」程度でこなせるようになるが、
今そこを目指してブランチを減らすと、グローバル汚染のリスクが跳ね上がる。

### Nix でワークスペースを宣言する

前節の `codex.nix` がそのまま正本の宣言になる。

ワークスペース一覧・信頼設定・clone を同じ `let` の `workspaces` リストで管理しているため、
カスタムモジュールやオプション定義を作る必要がない。
初回の `home-manager switch` でリポジトリが揃い、以降の `git pull` は各プロジェクトの責務だ。

## フロンティアモデルなしでは汚染は避けられない

ハーネスを丁寧に作っても、使うモデルの判断品質が低ければ環境汚染は起きる。

フロンティアモデル（現時点では claude-opus-4.x や GPT-4o 以上のクラス）でないと、
「このコマンドを実行するとどういう副作用があるか」の判断精度が十分でない。
結果として：

- devShell の外にパッケージをインストールしようとする
- `~/.bashrc` を直接書き換えようとする
- `npm install -g` や `pip install` をグローバルに実行する

ハーネスはこれを機械的に完全ブロックできない。
ブロックしすぎると作業が止まる。
**「モデルがそもそもやらない判断をする」ことに依存している部分が大きい。**

ハーネスエンジニアリングはフロンティアモデルを前提として設計する。
コスト削減のために非フロンティアモデルを使う場合、ハーネス側の制約をより厳しくする必要があり
（write 権限の絞り込み、実行前の確認ステップ追加など）、それ自体が別のトレードオフになる。

## ベンダーとプロジェクトの責務境界

Codex App（ベンダー）が提供する部分と、プロジェクト側が管理する部分を**先に**切り分けておく。
この切り分けをしないまま設定を積み重ねると、混線と肥大化によって技術負債が増える。

**ベンダー責務（原則として触らない）：**
- Codex App 自体のサンドボックス実装
- モデルの推論品質・コンテキスト理解
- MCP プロトコルの実装と仕様変更

**プロジェクト責務（宣言的に管理する）：**
- 信頼するプロジェクトパス（`config.toml`）
- 使うツールチェイン（プロジェクト devShells）
- 環境変数の橋渡し（WSLENV）
- GitHub ブランチ戦略とワークスペース定義

この境界が曖昧だと、「Codex の挙動がおかしいのはベンダーのバグか自分の設定のせいか」が切り分けられなくなる。
デバッグコストが指数関数的に増える。

一点だけ正直に書いておく。
**この境界の監視は自動化できない部分が残る。**
ベンダーが実装を変えれば前提が崩れる。
Codex App のアップデートのたびに確認するしかない。
これは避けられないランニングコストとして計上しておく。

## KISS 原則で削ぎ落とすもの

ドットファイルは肥大化しやすい。Codex ハーネスで実際に必要なものだけを書く。

**要る：**
- `programs.bash.enable = true` + `$SHELL` の固定
- `programs.direnv` + `nix-direnv`
- `home.activation.codexConfig` による config.toml 管理

**要らない：**
- starship（Codex のセッション中は見えない）
- zsh の autosuggestion / syntax highlighting（インタラクティブ専用）
- fzf のシェル統合（同上）
- カスタムシェルエイリアス群（Codex は自分で適切なコマンドを組み立てる）

プロンプトや補完設定はインタラクティブなターミナル用の話だ。
Codex セッションには不要であり、初期化コストだけかかって邪魔になることがある。

## まとめ

Codex App を Nix + home-manager で閉じ込める要点：

1. **シェルは bash に寄せる** — WSL 経由のシンボリックリンク・`$ZDOTDIR` 連鎖問題を避けるため
2. **パスは Linux 側に寄せる** — Windows ACL との摩擦を断ち切る
3. **ツールはプロジェクトの devShell に** — `home.packages` に入れない
4. **direnv で境界を引く** — プロジェクトに入ったらツールが有効、出たら戻る
5. **アクティベーションで config.toml を管理** — 信頼設定を宣言的に
6. **GitHub を正本にしてブランチを多めに切る** — 現行モデルのコンテキスト制限への適応
7. **フロンティアモデル前提で設計する** — ハーネスは判断品質を補えない
8. **ベンダー/プロジェクト責務境界を先に切る** — 混線が始まると負債は加速する

最後の項目だけは Nix で自動化できない。
ベンダーが変わり、モデルが変わり、前提が崩れる。定期的に確認するしかない。
それ以外は宣言的に管理して、`home-manager switch` 一発で戻れる状態を保つ。
